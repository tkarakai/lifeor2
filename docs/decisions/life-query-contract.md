# A query contract for family data

Status: implemented and evaluated with the existing local model. See the [versioned acceptance evidence](../evaluation/life-query-results-2026-09-18.md) for measured results, preserved failures and limits. This is not a claim of universal query coverage.

## Failure we are fixing

The original “What’s coming up this month?” run on test-data1 used the configured Qwen3.8-27B-8bit model with a 32,768-token context and 2,048-token output limit. The initial database reads took about 1.3 seconds. The model instead spent its five-minute budget reading old transactions and settled obligations, paging large results, and reaching a pending context-compaction step. Recorded input reached 23,515 tokens before timeout. There was no observed provider context-overflow error. Discovery also used substring matches, allowing “up” to match “update.” The global prompt was disproportionately about income.

The failure was not evidence that the database was too large or that a different model was required. It exposed a poor division of work between the model and server.

## Division of responsibility

The model interprets a question, resolves consequential ambiguity, chooses a small number of domain reports, and selects the report view. Financial answers are rendered by code from saved evidence, rather than asking the model to retype amounts. Qualitative answers can still use normal model prose. The server resolves local calendar dates, filters records, performs exact monetary arithmetic, follows database pagination, reconciles linked claims and forecasts, and reports coverage limitations. Neither record text nor saved conversation memory supplies instructions or authorization.

Twelve direct read tools cover workspace context, identities, relationships, events, upcoming commitments, financial reports, project costs, recurring terms and cash projections. Other read and write operations are discovered on demand with whole-word relevance scoring and separate read/write intent. The client loads compact workspace metadata deterministically before inference, saving a model round for local dates and household identity. A complete household member list does not establish unrecorded kinship.

Reports distinguish query completeness from completeness of the underlying real-life records. Currencies remain separate. Posted expense, capital acquisition, loan principal, transfers, gross income, actual payroll cash and forecast cash have distinct meanings. Ambiguous matches, incomplete scans and unsupported inferences are explicit, not fabricated zeros.

Real Qwen tests returned correct numeric evidence but sometimes relabeled paid cash as incurred cost or divided a monthly paycheck total twice. `reports.present` therefore produces the final factual text. The client exposes `present_report` and finishes the turn with that exact text, recording zero inference usage for rendering. Once a report has been retrieved, a free-form final draft is held back; the client requires a report-selection tool call instead. This does not solve wrong scope selection: household versus company books and subject versus beneficiary remain separate inputs and separate acceptance checks.

Financial calls require an explicit household/dataset scope at the MCP boundary. A household scope resolves the configured household's reporting chart; it never guesses from a surname. Category words can filter accounts without an extra ID-resolution round. Unknown or ambiguous scope fails explicitly.

A separate `reports.comparePeriods` operation takes two exact, non-overlapping periods and orders them chronologically on the server, then by default computes later minus earlier using identical filters and one verified data version. An explicit later baseline supports questions about an earlier period relative to a later one. The chronological default avoids reversing a change when the model swaps the arguments, and rejects a mistaken window spanning both periods. Overlapping-window requests can use separate totals instead of an ambiguous comparison. Ranked views group the full saved evidence before sorting and limiting; profit ranking uses net income and refuses incomparable currencies. Zero baselines do not produce invented percentages; currencies remain separate and unequal periods are stated without extrapolation. Superseded list/income tools remain available to external clients, but replacement metadata keeps them out of the new chat's discovery surface.

## Financial read model

Posted journals remain authoritative. Daily reporting cells aggregate equal dimensions: account, accounting date, chart, explicit or unambiguously inherited subject, arrangement, tag set, beneficiary basis, currency and event kind. Beneficiary allocations are a separate basis and are never added to the posting totals. Source examples remain bounded.

The scoped write layer tracks affected journals. Before a domain mutation commits, it subtracts old indexed contributions and inserts their replacements in that same transaction. This covers posting, attribution, beneficiary, event and direct-tag changes, including reversals and deletion. Account names and current arrangement-tag relationships are read at query time. New sample and named datasets opt into the index only when initialized correctly. Existing datasets use the source-query fallback until an operator completes the resumable `reportIndex:backfill` migration. Index readiness has a version, so a future representation change can fail over safely.

Indexes select posting/beneficiary basis, account, event kind and date before aggregation. Database pages are drained inside the service; they do not enter the model context. Every financial page reads a monotonic dataset revision in the same transaction as its rows. Named-dataset reports require identical revisions across all pages, establishing one data version without depending on the backend’s short historical timestamp retention. A changed revision aborts the report without publishing partial totals. Legacy scopes without revision coverage retain pinned Convex snapshots. Compound project/cash reports start with a pinned snapshot and may restart the financial scan with revision checks if that timestamp expires; their planning and financial revisions must also match. Period comparisons likewise require identical revisions. This relies on all supported data mutations maintaining the revision transactionally; operator code must preserve that invariant. Incomplete or inconsistent reports never return apparent final totals.

Saved reports are immutable, scoped by user, connection and dataset, stored outside source control with private permissions, and expire after 24 hours. A follow-up can inspect selected rows without putting the entire report into conversation history. Access is revalidated when reading a saved report. A saved snapshot is not presented as current data.

## Focused workflows

A transactionally maintained current-claim index keeps settled historical obligations out of upcoming queries. Existing datasets require `reportIndex:backfillObligations` before this index is used. Future settled claims remain available to suppress prepaid schedule occurrences.

`life.timeline` keeps party filtering separate from incoming/outgoing perspective: `entityId` narrows the involved party, while direction remains relative to the default household unless `perspectiveId` explicitly selects someone else. A tenant filter therefore cannot silently reverse a household receivable. It combines outstanding claims, linked expected cash, recurrence and recorded events, suppressing duplicates and preserving due dates versus expected dates. `life.events` provides indexed text/date/kind search when the question concerns particular occurrences. Relationships, revisions, measurements and source Markdown have separate compact reads. Role and arrangement-name filters return the verified counterpart participants with each relationship, avoiding serial identity lookups. Historical relationship dates use the end of the dataset’s local civil day. Measurement and event pages use date indexes and opaque cursors rather than loading years of records into reference-table arrays. A bounded subject probe selects the event-link index for small histories, bypassing unrelated financial activity; prolific subjects use the date index so old transaction links cannot bury recent events. Link-order results are explicitly labeled. Next-appointment queries omit an upper date boundary and return earliest-first; visible legacy/default-dataset events preserve that ordering. Measurement cutoffs can cover all recorded history without a guessed start date and return named subjects.

`reports.commitment` returns recorded effective recurring terms. A separate `reports.commitmentScenario` computes a user-proposed amount difference against the applicable recorded period without changing records. Separating actual and hypothetical contracts prevents optional scenario fields being filled with invented defaults. It renders inclusive local dates directly, avoiding model timestamp conversion.

`reports.project` combines tagged ledger activity, outstanding obligations, future unincurred assumptions and pinned source-note excerpts. With an explicit historical cutoff it reconstructs project claims from recognition, adjustment, settlement and reversal dates; claims without dated recognition evidence remain unknown. Project-specific indexes include claims already settled today. Expectations and source notes remain clearly labeled current snapshots. `reports.cashProjection` starts from recorded bank balances, uses explicit cash routes, exposes missing routes and individual-account shortfalls, and supports read-only hypothetical scenarios. Recurring changes replace future schedule amounts and compare against the unchanged baseline; separate one-off movements are additive. Incurred claims and historical cash never change in a scenario. When a contract has a separate net-cash override (such as payroll withholding), the service refuses to infer the net effect of changing the gross contract. It does not promise affordability or invent spending assumptions.

Writes continue through existing scope, idempotency and concurrency controls. Focused workflows accept civil dates/times and decimal monetary strings rather than asking the model to calculate timestamps or cents. Appointment corrections preserve history and subjects; schedule changes preserve later effective segments; paid expenses create balanced posted journals. Explicit card charges credit a designated credit-card liability without reducing bank cash; arbitrary loan liabilities are rejected. The client additionally checks the selected payment account against retained original user messages before dispatch, so a discovered sole account or model-generated memory cannot fill a missing user choice. DST gaps/folds, stale revisions, unknown accounts and missing consequential details require clarification or a specific conflict response. Posted transactions are corrected with reversals. Source-note additions can read metadata only and append against an immutable base commit; the server preserves the existing document and rejects conflicting concurrent changes. Retrying the same append against the same base cannot duplicate it.

## Open-source lessons

These projects were inspected for implementation patterns, not treated as proof of small-model accuracy. GitHub adoption snapshot on 2026-09-18: Home Assistant MCP 4,770 stars, DBHub 3,534, Google Workspace MCP 3,183, Google Calendar MCP 1,189, Actual MCP 232. The finance-specific project is smaller but closely relevant. These are selected popular/relevant implementations, not a claim of an exhaustive ranking:

- [Home Assistant MCP](https://github.com/homeassistant-ai/ha-mcp): relevance-based deferred discovery, pinned entry tools, compact versus detailed representations, and read/write separation.
- [Google Workspace MCP](https://github.com/taylorwilsdon/google_workspace_mcp): capability tiers and service-specific filters, bounded calendar pages, detail levels, and explicit cursors.
- [DBHub](https://github.com/bytebase/dbhub): a small discovery/query surface, selectable detail, parameterized operations and result caps. LifeOR2 uses typed reports rather than granting the model arbitrary SQL.
- [Google Calendar MCP](https://github.com/nspady/google-calendar-mcp): explicit timezones, filtered event reads and partial-failure handling. Its exact pagination behavior was not assumed correct without inspection.
- [Actual MCP](https://github.com/s-stefanov/actual-mcp): finance-specific filters and deterministic summaries; transfers and split transactions require domain meaning.
- [Anthropic’s tool-writing guidance](https://www.anthropic.com/engineering/writing-tools-for-agents): tools should return useful context and consolidate operations that agents otherwise perform repeatedly.

## Validation approach

Deterministic tests compare indexed answers with direct source-ledger scans, including currencies, attribution and account types; test atomic updates and reversals; check dataset isolation; and exercise calendar corrections and DST boundaries. Real-model tests use the actual production MCP handler, production client adapter, configured local Qwen model, and a separately deployed local Convex database. They preserve failed attempts and require semantic review; a completed response or presence of expected numbers alone is not sufficient.

Scale fixtures grow transaction history across 2010–2025 while keeping the household graph small. A second fixture varies household categories, amounts, banks, cards, subjects and beneficiaries; fully funded purchase/card-payment cycles independently reconcile to unchanged cash and card balances. Sample generation itself uses indexed monthly enrichment, avoiding cross-dataset scans and oversized final mutations. Every synthetic journal balances, generated income/expense totals have independent mathematical expectations, and synthetic cash reconciles into the original sample opening state. The evaluation deployment and its private credentials are isolated from the normal backend. At 1,000×, the target is 308,000 journals, not 308,000 people. Measured results and remaining limitations are recorded in the acceptance evidence linked above.


## Unknown-date lookups

An existing appointment can be located by title/subject with both dates omitted. A proposed replacement date is not a filter for its old occurrence. Explicit next-appointment questions still use `from=today` with no upper cutoff and chronological ordering. Calendar corrections update the stored display timezone as well as the UTC instant, while preserving prior records and subject links.

## Individual receipt lookup

Journal memo search uses a dataset/user-scoped full-text index, with optional dates and chart/person filters. Unknown dates are omitted rather than guessed. Convex full-text search matches any query term, so a bounded probe (33 hits per literal word, at most 16 words) selects a candidate stream and the service requires all words before returning a receipt. The selected stream and filters are bound into the continuation cursor. Empty filtered pages retain their cursor; they do not establish absence. Exact decimal posting amounts accompany ledger minor units. Aggregate questions still use report queries.

This follows the documented [Convex text-search semantics and limits](https://docs.convex.dev/search/text-search), rather than assuming that a multiword search implies conjunction. The non-staged `search_memo` index must finish its automatic backfill during deployment before the new query is served. It does not rewrite source journals.


## Exact calendar facts and source excerpts

Actual-model retests found correct event lookup followed by invented DST alternatives and swapped daylight/standard-time labels. Calendar queries now save verified event reports with exact local time, UTC offset and repeated-clock occurrence. Ambiguous appointment writes return typed `needs_input` choices before changing an event; the client displays that question verbatim and blocks later operations in the same batch. A user can select the second occurrence without doing offset arithmetic.

Source tests likewise found correct parking/cat facts followed by an unsupported claim about unread text. Source reads and note searches now save excerpt reports, which quote exact source text and its immutable commit, with explicit partial-document coverage. Note search ranks matching lines by distinctive words, so distant terms in a long document can be retrieved together without copying the intervening text. Model-generated prose cannot replace those source or calendar reports. Qualitative answers without such evidence remain ordinary prose; this is a factual-output boundary, not a claim of universal language understanding.


Successful writes return exact changed-record facts. Within the same turn, the client invalidates earlier report handles for final presentation; reading an old saved report does not refresh it. A new query is required to present updated records. Historical saved reports remain immutable evidence snapshots, not a cache of current truth. Repeated-edit inference cases verify the visible confirmation as well as the committed correction chain.


Current unpaid invoices have their own `life.obligations` query. It resolves named debtors and creditors in an explicit household/dataset scope, includes all due dates unless a cutoff is requested, and returns exact unpaid totals grouped by debtor, creditor and currency. It excludes projections and duplicate expected payments. This avoids asking the model to convert a cash-flow perspective or choose a historical timeline window to answer who owes whom. Loan principal and balance-sheet liabilities remain separate financial metrics.

Timeline queries with debt-status or cash-direction filters skip calendar events that cannot satisfy those filters. Incomplete timelines fail before saving a report; old incomplete snapshots also cannot be presented. Complete empty timeline lookups return absence evidence without a selectable report handle, so a repaired lookup cannot accidentally display the earlier empty attempt. Current-debt empty results still use exact rendering with explicit scope and missing-record semantics.


## Recoverable references and scoped source facts

A returned `details_document_id` is now directly readable as `details.read(documentId=...)`; `target` instead denotes the owning record and advertises its valid kinds. Exactly one reference form is required. Reads return the canonical target and immutable commit. An optional query scans that known document for any normalized query word and returns bounded exact matching lines. A complete empty match is scoped to the document and words; a missing document is not a completed search. Full pages and metadata remain available, with commit-pinned continuation. This prevents repeated invented document target kinds and avoids loading an entire long profile for one fact.

The original-user account guard distinguishes a missing choice from an unresolved reference. A supplied suffix/name that is not a stable ledger-account ID produces a recoverable error and no execution, permitting lookup and retry. A verified account that the original user never selected still requires clarification. Neither model summaries nor retrieved notes authorize that choice.


A retrieved report can be related without answering the question. `reports.present(conclusion=insufficient_evidence)` emits a fixed, limited statement that the retrieved records did not establish the requested answer, followed by unchanged verified evidence. It does not accept invented free-form conclusions or claim exhaustive absence. Source guidance permits one focused synonymous follow-up, then this conclusion; guessed candidate values and exhaustive unrelated paging are not a way to prove a missing fact. Positive source retrieval and negative evidence adequacy require separate actual-model tests.


Mixed-direction testing exposed that an optional debtor/creditor filter was too easy to omit. The MCP contract now requires `direction=receivable|payable|both`: owed to the selected perspective, owed by it, or both sides. Household scope supplies the configured household; `perspectiveQuery` uniquely selects another person/company. Dataset scope without a named perspective can use `both` plus explicit party filters. `partyQuery` narrows involved parties and never changes perspective. Reports label the chosen direction/perspective explicitly. Backend callers omitting direction retain the original both-sides behavior; new MCP calls must choose intentionally.

In addition to the primary reads and up to two relevant edit schemas, the client exposes up to two relevant source-read schemas directly. This uses the existing authorized catalog relevance scoring, not a hard-coded answer or a raw-data prefetch. It avoids malformed nested generic-call envelopes for common profile facts while retaining the same argument validation, dataset binding and read permissions.


Calendar writes now produce fresh verified receipts, including linked participants, the actual weekday/offset and preserved correction history. Participant selection is explicit in the MCP create schema; a title containing a name is not a relationship. A storage failure after a committed write returns a verified confirmation instead of suggesting the mutation failed. Timelines with missing household perspective or timezone return typed clarification before collecting records; an explicit user-supplied perspective/timezone can answer it without changing workspace settings.

Relative calendar phrases use the same division of responsibility. The service accepts an absolute `date` or a bounded `dateExpression` and resolves relative civil days in the selected timezone. “Next Tuesday” is the next strictly future occurrence; “two days later” is relative to the selected existing event; `time=same` preserves its local clock time. The client retains a recognized simple expression from the current original user request before validation and idempotency hashing, so a guessed absolute date cannot override it. Mixed origin/destination, negated, quoted-title and explicit-date clauses are not automatically rewritten. The supported grammar is intentionally bounded; unsupported expressions need an explicit date or clarification. The independent actual-model oracle checks the committed instant, canonical `Appointment` category, participant link and complete correction chain.

Receipt results include the journal’s chart and query filters as well as full posting amounts/accounts. A `singleExactMemoMatch` signal is conservative: only one normalized whole-memo match on a complete first page qualifies. Later pages and multiple/partial matches do not establish uniqueness. This addresses a real-model regression in which the correct receipt arrived immediately but the model unnecessarily searched unrelated company books. Exact-match guidance encourages answering from the already sufficient record without blocking legitimate follow-up questions. Project report rendering also states that recorded costs, budgets and milestones cannot establish or guarantee completion timing.
